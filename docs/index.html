Application guide

Start here#

HLUSCA supports the daily work of a Savings and Credit Cooperative: enrolling members, recording savings, processing loans and repayments, recording investments, and distributing approved dividends. Amounts are shown in Uganda shillings (UGX).

This handbook documents the code included with this copy. It includes the current investments and dividends implementation. Its source fingerprint identifies the reviewed application files; it does not establish which migrations or version a deployed instance is running.

What is available in this iteration#

Membership, savings ledgers and exports, loan products, applications, approvals, retained agreements, signatures, disbursement, schedules, repayments, statements, the overdue job, investments, and dividends are implemented in the current working tree.

The Board and Administrator landing pages contain summary counts. The full audit-log viewer and portfolio reporting workspace are still planned in the build specification. Their descriptions in the specification or sidebar text do not create additional screens. There is no implemented loan-cancellation button, repayment correction/waiver workflow, automatic investment-return payout, or general notification-delivery service.

Application guide

Getting started#

Sign in#

  1. Open the application address supplied by your cooperative. The sign-in page is /sign-in.
  2. Enter your member number, username, phone number or email in the identifier field. Use the international phone format, for example +256700000123.
  3. Enter your password and select Sign in.
  4. If instructed to change a temporary password, complete that step before opening your dashboard.
  5. After sign-in, the application directs you to the landing page for your assigned role.

Your Administrator supplies the original member number, username and temporary password. A suspended login cannot sign in. Membership status and login status are different: a newly enrolled PENDING member has an active login and can view their information before first savings activation.

First sign-in and password changes#

  1. On Change password, enter your current temporary password.
  2. Choose a new password with at least 10 characters, one lowercase letter, one uppercase letter, one number and one symbol. Confirm it in the form where prompted.
  3. Submit the change. The application clears the first-login requirement.
  4. Sign in again when the form redirects you, using your new password. This establishes fresh session information.

You can also open /change-password while signed in. The current password is always required. The application never asks you to share that password with another role as part of approving a loan or dividend: Treasurers confirm their own passwords when disbursing or posting.

Recover a forgotten password#

  1. Select Forgot password from sign-in, or open /forgot-password.
  2. Enter the same identifier you normally use to sign in and request recovery.
  3. Follow the channel and token/code instructions shown. The pilot displays a preview reset token when one is generated.
  4. Enter the token/code and a new strong password, then submit the reset form.
  5. Return to sign-in and use the new password.

A reset token expires after 15 minutes and can be consumed once. Email is preferred when the account has an email address; phone is the next choice. The current implementation stores notifications and returns a preview token; it does not send email or SMS. If the form indicates administrator-assisted recovery or no usable token, contact the cooperative Administrator. There is no dedicated administrator-assisted reset screen implemented yet.

Find your way around#

On a computer, use the left sidebar. It can be collapsed into icons; expand it to see menu names. On a phone, select Open navigation in the top bar, choose a destination, then close the drawer if needed. The application remembers the desktop sidebar preference on that browser.

Sign out and role changes#

Use Sign out in the sidebar when finished. After an Administrator changes your system role, sign out and sign in again so the navigation and session reflect that role. Some financial handlers reload your current account from the database, while other pages and APIs read the session's existing role claim; an old session can therefore show an outdated menu or reject an action.

Members and administration#

Administrator: enroll a member#

  1. Sign in as Administrator and choose Members.
  2. Open the enrollment action to reach Enroll a new member at /dashboard/admin/members/new.
  3. Enter first and last names, username, phone, address, national ID, and next-of-kin name and phone. Email, birth date and photo URL are optional.
  4. Use international phone numbers with a leading +. Choose a unique username of 3–32 characters using letters, digits, dots, underscores or hyphens.
  5. Submit the enrollment form. Correct field errors such as an existing username or phone number, then submit again.
  6. On success, record the displayed member number and temporary password for handover to that member. The result also identifies the credential delivery method.
  7. Open the new profile to verify the details. The member must change the temporary password at first sign-in.

Enrollment creates three linked records in one transaction: a PENDING member, an ACTIVE CLIENT login requiring a password change, and an ACTIVE savings account with zero balance. It also stores a welcome notification and an audit event. The current notification implementation does not send SMS; arrange the actual credential handover through the cooperative's process.

Administrator: find and update a member#

  1. Choose Members and search by member number, name, phone or username.
  2. Open the required record and verify the displayed member identity.
  3. Edit the relevant fields under Member profile. Administrator fields include identity details, Status, System role and contact details.
  4. Select Save profile and check the success message.
  5. Refresh the profile to verify the saved linked role. Ask a user whose role changed to sign out and sign in again.

You cannot change your own system role. Changing membership status here does not automatically suspend the linked login or savings account. The pilot does not expose a general-purpose staff-account administration screen; this form manages a login linked to a member. The bootstrap command is used separately for initial administrator setup.

Member: update your contact information#

  1. Choose Profile from the sidebar.
  2. Update address, phone, email or next-of-kin details.
  3. Select Save profile.
  4. Confirm that the updated contact information appears.

Members can update their own contact fields only. Names, national ID, member status and system role require an Administrator. A changed phone or email can affect the identifiers used for sign-in and recovery.

Savings and ledgers#

Member: view your savings#

  1. Choose Dashboard.
  2. Review the primary savings balance, member number and account status.
  3. Scroll to Transaction log for individual entries. The dashboard also shows savings activity summaries and posted dividend history.
  4. Use the transaction search, type and date filters to narrow the log. Search can match references, notes or the recorded-by information exposed by the ledger.
  5. Use the page controls to move through results, or Export CSV / Export PDF for a download of matching entries.

The current balance is the account balance, not a total of only the rows visible on the current page. Deposits, loan disbursements and posted dividends can increase savings. The separate loan-payment receipt workflow does not reduce savings.

Treasurer: locate a member ledger#

  1. Choose Treasurer Desk.
  2. Review the savings summary, member ledgers and recent activity.
  3. Search the member-ledger list and open the intended member.
  4. Verify member number and savings account before recording an entry.
  5. Use the member ledger's back link to return to Treasurer Desk after completing the task.

The desk and ledger provide Record deposit and Record withdrawal actions. On a smaller screen, some table content appears as cards or in a horizontally scrollable list.

Treasurer: record a deposit#

  1. Locate the member and select Record deposit.
  2. Enter a positive amount with no more than two decimal places.
  3. Enter a useful Reference and Narrative, such as the receipt identifier and reason. Reference is limited to 80 characters, narrative to 240.
  4. Verify the member and amount, then select Post deposit.
  5. Wait for the success message and confirm that the balance and transaction log update.

The account must be ACTIVE. A deposit on a PENDING membership also changes that membership to ACTIVE. The ledger entry, balance change, membership activation where applicable, and success audit commit together.

Treasurer: record a withdrawal#

  1. Locate the member and select Record withdrawal.
  2. Enter amount, reference and narrative.
  3. Compare the requested amount with available savings.
  4. Select Post withdrawal and verify the success message, new balance and WITHDRAWAL entry.

Withdrawals cannot exceed the available balance. The current savings handlers require an active savings account; they do not impose the loan-specific restriction against a Treasurer acting on their own account. A membership status change alone does not close or suspend that account.

Exports and dates#

Savings exports include every matching ledger row, not only the current page. JSON accepts pageSize from 1 to 100, default 8; exports ignore pagination. The savings export route currently does not create an EXPORT audit event. Loan application and statement exports have their own audited implementation.

Savings filter date boundaries use the server's local date operations. Repayment calendar dates and dividend daily-balance calculations explicitly use Africa/Kampala. When reconciling a boundary-date discrepancy, consult the stored transaction timestamp and deployment timezone with an operator.

Savings references are descriptive and are not enforced as unique idempotency keys. Repeating a deposit or withdrawal request can create another entry. This differs from loan receipts, whose reference is unique within the loan.

Loans and repayments#

The loan journey#

  1. Member submits an eligible application
  2. Treasurer reviews; Board also reviews when the frozen threshold requires it
  3. Final approval creates the agreement; Member reviews and signs
  4. Treasurer confirms password and disburses to savings
  5. Treasurer records external repayment receipts; Member follows the statement
  6. Loan closes when scheduled principal and interest are fully repaid

Rejection ends the application's review path and records a reason. A product edit does not rewrite an application already submitted. Loan, application, contract and schedule statuses describe different stages; see the status table below.

Administrator: configure loan products#

  1. Open Loan Configuration.
  2. Under Create loan type, enter a name, interest method, annual interest rate, maximum term, maximum multiple of savings and processing fee percentage.
  3. Select Create loan type. No loan products are seeded with assumed terms, so this is required before members can apply.
  4. To change a product, open its edit action and select Save loan type. Deactivate a product when it should no longer accept new applications.
  5. Set the Board approval threshold and select Save threshold.

Interest rates are annual percentages; monthly interest uses the annual percentage divided by 12. The threshold includes equality: an amount equal to or above it requires both Treasurer and Board approval. Lower amounts require Treasurer approval only. Application submission freezes the product terms and threshold; changes affect new applications.

Member: apply for a loan#

  1. Open Loans, then its application action to reach /dashboard/loans/apply.
  2. In Loan & amount, choose a loan type and enter the requested amount. Select Continue.
  3. In Terms & purpose, choose the repayment term and explain the purpose in at least 10 characters. Select Continue.
  4. In Review & submit, review eligibility, fees, savings credit, total repayable and schedule preview. Use Back if something needs correction.
  5. Select Submit application when eligible.
  6. Open the application in Loans to follow its approval steps and any rejection reason or recent notification.

Eligibility requires active membership and savings account, an available product, a term within the product limit, and enough savings for the product's lending multiple. The preview explains why an application is ineligible. It is recalculated on submission and eligibility is checked again at disbursement. The pilot does not place collateral holds on savings.

Treasurer and Board: review applications#

  1. Choose Loans. The staff review queue defaults to Awaiting my review for Treasurer and Board.
  2. Use search, status and date filters to locate an application.
  3. Open its details; review the applicant, amount, purpose, product terms and approval steps.
  4. Enter a Review comment (required when rejecting). Rejection needs at least three characters.
  5. Choose the displayed approval action or Reject application. For the Treasurer's first step in a two-stage chain, the approval action indicates a recommendation to the Board.
  6. Read the confirmation dialog and select Confirm approval or Confirm rejection.
  7. Check the updated status and approval history.

Only the role for the next pending step can decide. The Treasurer must review before the Board. A reviewer cannot act on their own member application, and one person cannot complete both steps by changing roles. Once a final approval succeeds, the agreement is created automatically.

If an approved application disappears from your review queue, clear Awaiting my review to find it. Administrator can inspect applications, but does not receive Treasurer or Board decision controls.

Member: review and sign the agreement#

  1. Open the approved application from Loans.
  2. Read the complete agreement, product terms, fee, net credit and repayment preview. Open the agreement PDF for the retained document.
  3. Under Sign your agreement, type your full name exactly as shown on the contract.
  4. Draw your signature in the signature area. Use its clear/reset action if necessary.
  5. Select the agreement checkbox and choose Review and sign.
  6. Review the confirmation, then select Confirm and sign.
  7. Verify the displayed signed name, timestamp and signature.

The server validates the PNG image, name, consent, contract ownership, active membership and document hash. The original PDF is retained unchanged. Signing stores the signature and evidence for that exact document; the application does not expose a signature-edit action afterward. Actual schedule dates are fixed when disbursement occurs.

Treasurer: disburse funds#

  1. Open Loans and clear Awaiting my review if needed.
  2. Open the approved, signed application. Review the amount shown under Disburse this loan.
  3. Select Review disbursement.
  4. Verify the member, gross principal, withheld fee and resulting savings credit.
  5. Enter your own password under Confirm your Treasurer password.
  6. Select Confirm and disburse.
  7. Confirm that the Loan and repayment schedule appear and the net credit is visible in savings.

A Treasurer cannot disburse their own loan. The server rechecks approval, signature integrity, active membership/account and savings-based eligibility. It creates the Loan, complete monthly schedule, savings credit, notification and audit together. Repeated disbursement requests are rejected.

For example, a principal of UGX 300,000 with a 2% processing fee credits UGX 294,000 to savings. The principal repayable remains UGX 300,000, plus the scheduled interest. This example illustrates behavior and does not prescribe product terms.

Treasurer: record a repayment#

  1. Open the disbursed application from Loans and find its repayment workspace.
  2. Enter the amount, actual calendar payment date, payment method (cash, bank transfer or mobile money) and receipt reference.
  3. Choose a target installment only if that receipt should prioritize a specific installment; otherwise use normal allocation order.
  4. Review the payment details using the form's review action.
  5. Check the confirmation and select Confirm payment.
  6. Verify the receipt, installment matches, outstanding balance and updated schedule.

Another Treasurer must record a Treasurer-member's own loan receipt. The payment date must fall between disbursement and today in Africa/Kampala. References are trimmed and uppercased, and must be unique within the loan. An amount above one installment can cover later installments, but an amount above the entire scheduled balance is rejected.

Receipts record funds received outside the savings ledger; they do not debit savings. The receipt itself is immutable, and the pilot does not include a correction, deletion or waiver workflow. Check all details before confirmation. After an interrupted submission, inspect the statement before repeating the request; a duplicate reference produces a conflict instead of another receipt.

How payments are matched#

Normal matching starts at the oldest unpaid installment. It pays interest before principal within each installment, then continues to later installments. A selected target installment, or a reference such as INST-3/DEMO-RECEIPT-123, prioritizes installment 3; any remainder then follows normal due-date order.

Partial payments preserve the exact remaining principal and interest. An overdue installment that is partly paid remains overdue. The final payment closes the loan when its scheduled balance reaches zero.

Backdated receipts cause all receipts to be replayed by payment date, recording timestamp and ID. This can change previous allocation matches; original receipt records remain unchanged. The audit captures the before/after allocation state.

View and export a statement#

  1. Open a disbursed application and its repayment statement.
  2. Filter by date range, type or reference. The statement's type filter uses disbursement and payment rows.
  3. Review principal, interest, amount, running balance and installment allocations.
  4. Use pagination for more rows, or the CSV/PDF export action for the current filters.
  5. Use the PDF's complete current schedule to compare receipts with future or overdue installments.

Members see their own statements; staff can inspect all. The running balance includes earlier transactions outside the chosen filters. Opening debt includes the full contractual principal and interest. Exports are audited and limited to 5,000 matching rows; narrow the filters if necessary.

Investments and dividends#

Administrator: create an investment product#

  1. Open Investments.
  2. Under Create investment product, enter name, description, expected annual return percentage and risk profile.
  3. Choose whether the product is active and select Create product.
  4. To change a product, use its edit action and select Save product. Deactivate it when it should no longer be offered for new holdings.

Expected return is stored as a product term; it does not schedule a payment or guarantee a result. Risk profile is LOW, MEDIUM or HIGH. Product names must be unique. Existing holdings retain their recorded product name, rate and risk when products are edited.

Administrator: record an investment#

  1. In Investments, find Record member investment.
  2. Select an active member and an active product.
  3. Enter the principal, start date and maturity date. Start cannot be in the future; maturity must be after start.
  4. Check the member, product and amount, then select Record investment.
  5. Verify the ACTIVE holding appears in the holdings list.

These are records of investments funded outside this savings ledger. Recording a holding does not debit savings or transfer funds. The holding stores a snapshot of the product terms at the time it was recorded.

Administrator: close a holding#

  1. Locate the ACTIVE holding in Investments.
  2. Choose its maturity action when the maturity date has been reached, or Cancel investment when the record should be cancelled.
  3. Review the selected status and choose Confirm status.
  4. Verify MATURED or CANCELLED in the list.

The server checks maturity against the Kampala calendar date. Already closed holdings cannot be closed again. Closing a holding does not automatically pay principal or returns into savings.

Member and staff: inspect investments#

Members choose Investments to see their own holdings and posted dividend history. Treasurer and Board have read access to holdings across members; Administrator also has product and holding controls. Use search in the holdings table to locate a member, product or holding. A Member cannot obtain another member's holdings or dividend history by changing the URL or API filter.

Dividend workflow#

  1. Treasurer chooses a completed financial year and dividend pool
  2. Application calculates and freezes eligible member allocations
  3. Board approves or rejects with a comment
  4. Treasurer confirms password and posts an approved run
  5. Savings balances receive credits; posted history becomes visible to members

The creator cannot review their own proposal, even after changing to Board. A run's approver cannot post it after changing to Treasurer. The Treasurer who created a proposal may post it after a different Board reviewer approves it.

Treasurer: calculate a proposal#

  1. Choose Dividends.
  2. Enter the ending financial year, inclusive start and end dates, and total pool.
  3. Select one completed 12-month year. The default is January–December of the previous year. Financial year must match the period's ending year.
  4. Submit the calculation form and wait for the proposal to appear.
  5. Choose Review for that financial year to inspect member allocations, average savings and the total.
  6. Have a Board user review the frozen proposal.

The current method is PRO_RATA_AVERAGE_DAILY_SAVINGS. Another nonrejected run cannot overlap the same dates. A rejected proposal may be replaced. The calculation requires eligible members with positive average savings and a complete savings history, including opening balances.

How the proposal is calculated#

Each member's daily closing savings balance is determined in Africa/Kampala from the UTC ledger. The calculation includes all days in the year, leap days and zero days before their first savings. It averages those balances and allocates the pool proportionally across eligible members.

Eligibility is fixed at proposal time: active membership, active savings account opened before year-end, and positive average savings. The current balance alone is not used as a shortcut. The service saves exact balance-day weights and rounded shares; largest remainders allocate every cent of the pool with stable member-ID tie breaking. A rounded zero share is retained without a zero-value savings transaction.

Later savings activity does not recalculate an approved proposal. Before posting, the service rechecks recipient member/account status and the integrity of the saved allocations. A recipient becoming inactive blocks the whole posting transaction.

Board: approve or reject a proposal#

  1. Open Dividends and choose Review for the intended financial year.
  2. Review the inclusive year dates, pool, calculation method and member allocations. Use the allocation search where helpful.
  3. Choose Approve dividend run or Reject proposal.
  4. Enter a comment of at least three characters in the decision dialog.
  5. Confirm the decision and verify the resulting APPROVED or REJECTED status.

Only PROPOSED runs can be decided. Board cannot directly credit financial records from this screen. Administrator can inspect runs but cannot approve or post them.

Treasurer: post an approved run#

  1. Open Dividends, then review the APPROVED financial-year run.
  2. Choose the posting action and review its confirmation dialog.
  3. Enter your own password under Confirm your password and select the confirmation checkbox.
  4. Select Confirm posting.
  5. Verify POSTED status, the member allocations and resulting dividend history or savings entries.

Posting commits allocations, positive dividend credits, savings balances, posted state and one audit event together. Repeated or concurrent posting cannot pay the same run twice. If posting fails, inspect the specific error and resolve its cause before trying again; a changed recipient status or inconsistent allocation requires investigation.

Member: find dividend history#

Open Dashboard for posted dividends alongside savings, or Investments for the history shown there. Proposed and approved-but-unposted runs do not appear in member history. Each posted entry identifies the financial year, amount and average savings used.

API conventions#

Scope and identifiers#

The endpoint reference lists every explicitly exported HTTP method in the application route files. A route file may support several operations. NextAuth's catch-all delegates subpaths to the installed NextAuth implementation; its two exported handlers are counted once each rather than inventing separate application route files. Next.js can supply protocol behavior such as automatic OPTIONS handling; only explicit method exports are counted here.

Session and scheduler authentication#

The app uses NextAuth Credentials with JWT session cookies. Sign in through /sign-in using identifier and password. Session claims include user ID, role, status, memberId and first-password-change requirement. Use the installed NextAuth client helpers for sign-in/sign-out and CSRF handling; this app does not expose a bearer-token login API.

The catch-all forwards to authHandler in the local authentication options. Examples of delegated resources include GET /api/auth/session, /api/auth/csrf, /api/auth/providers, and POST /api/auth/callback/credentials and /api/auth/signout. Their framework-managed requests and responses are separate from the business API contract.

Business APIs require a session except password-reset request/confirmation. /api/auth/change-password allows the first-password-change state. /api/cron/loans/overdue authenticates with Authorization: Bearer <CRON_SECRET> instead of a user role or cookie.

withRouteAuth checks the session role and first-login state. The loanRead and loanMutation wrappers reload an active user from the database and check current role/status. Some custom export handlers use the same active-user resolver. proxy.ts performs additional redirects or early authentication rejection. This distinction matters after role/status changes: start a fresh session to update navigation and older session-based guards.

Requests and validation#

Use Content-Type: application/json for application mutation requests. Loan and investment/dividend mutations additionally enforce JSON content type, a 400,000-byte body limit, valid JSON, same-origin checks when an Origin header is supplied, and rejection of cross-site fetch metadata. Their success responses return the mutation result directly, not an extra { result: … } envelope.

The validation reference contains exact schema expressions, transformations and helpers. It is generated without importing the application runtime. Service checks still enforce ownership, state, eligibility, uniqueness and confirmation requirements beyond field schemas.

Loan/investment/dividend monetary writes use decimal strings, such as "50000.00", with at most two decimal places. Savings writes accept strings or numbers; strings are preferred. Rates are percentage strings. Date-only inputs use the formats documented per operation; serialized timestamps are ISO values. Do not send JavaScript floating-point calculations as an assumed exact monetary result.

PATCH for loan types and investment products takes the complete product payload. Member profile PATCH allows selected optional fields. Investment close PATCH takes only the closing status. Unknown investment/dividend payload fields are rejected by strict schemas.

Responses and errors#

Business successes currently use status 200, including record creation. The reference describes each shape. Prisma Decimal values serialize to strings; nullable fields remain null. CSV, PDF and PNG endpoints return bytes and the listed Content-Type rather than JSON.

Retry and confirmation behavior#

Disbursement and dividend posting reject repeats after completion and serialize competing attempts. Loan payment references are normalized and unique within a loan. Savings references are not unique keys, and repeating a savings write can create another entry. After a timeout, inspect the record/ledger before deciding whether a new request is appropriate.

Loan disbursement and dividend posting require the Treasurer's password and confirm: true. Loan payments require confirm: true; signing requires agree: true and the retained document hash. These controls do not substitute for server-side role and ownership checks.

const passwordComplexity = {
  minLength: 10,
  lower: /[a-z]/,
  upper: /[A-Z]/,
  digit: /\d/,
  symbol: /[^A-Za-z0-9]/,
};

export async function hashPassword(password: string) {

  return hash(password, 12);

  return compare(password, passwordHash);

export function assertStrongPassword(password: string) {
  const failures: string[] = [];

  if (password.length < passwordComplexity.minLength) {
    failures.push(`at least ${passwordComplexity.minLength} characters`);
  }

  if (!passwordComplexity.lower.test(password)) {
    failures.push("one lowercase letter");
  }

  if (!passwordComplexity.upper.test(password)) {
    failures.push("one uppercase letter");
  }

  if (!passwordComplexity.digit.test(password)) {
    failures.push("one number");
  }

  if (!passwordComplexity.symbol.test(password)) {
    failures.push("one symbol");
  }

  if (failures.length > 0) {
    throw new ApiError(
      `Password must include ${failures.join(", ")}.`,
      400,
      "WEAK_PASSWORD",
    );
  }
}

  1. Page and React component: present records, forms and navigation
  2. Route handler: authenticate request, validate input and format response
  3. Domain service: enforce ownership, workflow and financial rules
  4. Prisma transaction and PostgreSQL constraints: persist records and audit

Data relationships#

  1. Member links to a login User and one SavingsAccount
  2. SavingsAccount has Transaction entries and a current balance
  3. LoanApplication has ordered LoanApprovalStep records and a LoanContract
  4. Disbursement creates Loan, LoanSchedule and a linked savings credit
  5. LoanPayment receipts are allocated to installments through LoanPaymentAllocation
  6. DividendRun proposals freeze shares; posting creates DividendAllocation and savings credits

MemberInvestment links a member and investment product while retaining the original terms. AuditLog records actor, action, entity, success/failure and snapshots. Notification and PasswordResetRequest support access and workflow messages. SystemSetting stores operational settings such as the approval threshold. See the generated data dictionary for every model, field and enum.

Financial integrity and audit scope#

runAuditedMutation writes successful business changes and the success audit in one transaction; failures roll back and attempt a separate failure audit. Failure logging can itself be unavailable if the database is down. Earlier proxy/route guard denials do not all pass through the same audited wrapper; the handbook does not claim every failed request is audited.

Savings writes lock the account. Repayments and overdue updates acquire Loan locks before schedule changes. Disbursements lock application/account records; dividend proposals serialize period creation and postings lock runs and recipient accounts. Existing lifecycle integration tests exercise concurrency and rollback behavior.

Database migrations protect retained contract/signature evidence and immutable loan receipts. Payment allocation rows can be recomputed after backdating while receipt records remain unchanged. The build specification's broader audit-role privilege review is still a pilot-readiness item; there is no implemented audit viewer. Operators must use authorized database/log tooling to inspect audits.

Contracts and signatures are stored privately in PostgreSQL for the pilot and served through authenticated routes. The original agreement PDF is hashed and retained unchanged. PDF text supports Latin-1; names outside that range are represented with explicit Unicode code points in the PDF while the on-screen agreement retains the original name.

Migrations and deployment#

Apply all committed migrations before serving an updated application. The current investment/dividend code requires the Phase 6 migration as well as the preceding membership, savings, loan and repayment migrations.

npm run db:generate
npx prisma migrate deploy
npm run build
npm run start

Use npm run db:migrate when authoring a new migration locally. Use prisma migrate deploy for committed migrations in deployment. The GitHub Actions workflow validates pull requests and main pushes, then runs a serialized migration job on successful main pushes. Its production database environment bindings are currently commented out; configure secrets and the job's environment before relying on that migration stage. The existence of that workflow does not establish successful deployment or backups.

The handbook is built and checked in CI as a local artifact. It is not automatically published as a public application route. Download the HTML artifact or open docs/index.html from the repository.

Daily overdue job#

The committed schedule invokes GET /api/cron/loans/overdue daily at 00:00 UTC, which is 03:00 in Kampala. Configure CRON_SECRET and deploy the scheduling configuration to register it. On another host, configure its scheduler to send the same bearer-authenticated request. The function's declared maximum duration is 60 seconds.

The job flags PENDING/PARTIAL installments earlier than today's Kampala date on ACTIVE/DEFAULTED loans. It preserves paid, waived, closed and due-today installments. It does not change the amount owed, add penalties or default loans. Busy loans are skipped and reconsidered on a later invocation. Successful zero-change runs and failed attempts reaching the handler are audited under LoanSchedule with job: loans-overdue.

For failures, inspect function logs and the audit outcome, correct configuration or database issues, then retry the authenticated endpoint. Do not put the bearer secret in URLs or documentation examples. See job operations.

Known pilot boundaries#

Password recovery exposes preview tokens and notification records are stored without email/SMS delivery. Membership changes do not synchronize login/account suspension automatically. Savings exports have no EXPORT audit event; some early authorization failures bypass mutation auditing. Staff-only account management, a full audit viewer, portfolio reporting, receipt corrections/waivers and automated investment proceeds are not implemented screens. Backup retention, monitoring integration, broad security review and operational sign-off remain deployment responsibilities tracked by the build specification.

Update documentation with an application change#

  1. Change the application and run npm run docs:check to see affected review groups or newly undocumented routes/pages.
  2. Update the relevant user guide, endpoint catalog entries, screen descriptions and examples. Verify what the server actually enforces, including service-level conditions and any database constraints.
  3. Run npm run docs:generate to refresh route, action, navigation, validation and data references. Unknown route patterns and missing operation/page entries fail rather than disappearing silently.
  4. Acknowledge the reviewed source groups with a meaningful explanation. Only acknowledge after reading the changes and updating the guide or confirming that its instructions remain accurate.
  5. Build the HTML and run the documentation checks. Commit source documentation, review state and generated artifacts with the application change.
npm run docs:review -- loans --note "Reviewed the revised repayment allocation behavior and updated the loan guide and endpoint conditions."
npm run docs:build
npm run docs:check
npm run docs:test

For a broad change, list several groups before --note. --all is available for a deliberate complete review. The named groups are access, members, savings, loans, investments and technical. New files under mapped directories are included automatically. A new source outside all mappings fails the check and must be assigned a group.

The generate/build commands do not silently acknowledge source changes. Build and check require current review fingerprints. Even a change that does not alter instructions needs a brief review note explaining why the guide remains accurate. Git shows the review-state delta alongside the code change for review.

Add a page or endpoint#

Add its description to docs/catalog.mjs. HTTP operations use keys such as POST /api/loans/{id}/payments; page paths use the same brace syntax for dynamic parameters. Choose the correct authentication kind and screen association. Literal roles on supported wrappers are extracted automatically. Document additional ownership/state/separation-of-duties rules in conditions and, where necessary, a reviewed narrower policy.

The matrix and endpoint reference are rendered from the same combined record. Do not copy separate role tables into multiple guides. Keep procedural explanations in guides and link to the generated matrix. Custom authentication, conditional roles and delegated handlers require explicit reviewed metadata. Extend the extractor and its tests when introducing a new wrapper or export convention.

Add new code ownership to docs/config.mjs where necessary. Run generate, review, build and check. Verify that the page appears in the screen directory and every exported method appears in the endpoint reference. Mark API-only operations clearly when the UI has no action button.

Supported Markdown#

Use ATX headings (#, ##, ###), paragraphs, flat ordered/bulleted lists, Markdown tables, fenced code, bold text, inline code, links and local PNG/JPEG/SVG images. Tables must have a separator row and matching cell counts; escape literal pipes with a backslash. Heading names must be unique within a chapter. Use relative links between guide files and heading anchors; the HTML build rewrites them to internal bookmarks and validates them.

Use a fenced block with language flow for a small ordered workflow: write one stage per line. The renderer produces numbered flow cards that wrap on mobile and print in order. Raw HTML is escaped. Nested lists, raw embedded scripts, remote images and richer Markdown extensions are not supported. This limited renderer uses the existing Node/TypeScript toolchain and adds no runtime dependency to the application.

Screenshots should show synthetic records or public screens. Save them in docs/assets, add meaningful alt text and a caption explaining their task. Verify menu/button names against the source after a UI change. The compiler embeds images as data URLs; a copied HTML remains self-contained.

What CI checks#

CI checks source coverage, per-guide source reviews, the operation/page catalog, navigation destinations, generated file freshness and internal links. It runs meaningful generator tests for added/removed operations, guard roles, nested routes, changed source detection and unsafe/broken Markdown. It uploads the verified HTML as a workflow artifact after validation.
